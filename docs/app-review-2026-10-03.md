# Application review and improvement delivery

Reviewed on 3 October 2026 (Australia/Sydney). Base: remote `DevBranch`, commit `53232300a9a5bc7571045c697930384897604211`. This review deliberately excludes the separate Quant Analysis Studio branch. Proposed changes are delivered as independent, unmerged PRs; this document does not claim that proposals are already deployed.

## Assessment

The app already has useful feature boundaries, adjusted-close analytics, server-side ranking, explicit unavailable metric states, saved research views, and versioned Supabase policies. The highest-value next work is data integrity and recoverable account state, followed by reproducible development checks. A wholesale framework or visual-system rewrite is not justified by the evidence.

The review found four consequential behavior defects, an affected Next.js dependency, unbounded market-history cache retention, and missing development-branch gates. Read-only database inspection also found deployment drift that application code alone cannot repair. Every finding below distinguishes a reproduced defect, a source-supported risk, and a recommendation.

## Research method

Start from the actual checkout, manifests, CI, existing issues, and a running browser. Give independent reviewers bounded responsibilities and require a trigger, execution path, expected result, and confidence before accepting a finding. Preserve a baseline failure, implement a cohesive repair, verify affected boundaries, inspect the diff, and obtain a separate review. This follows [OpenAI's agent guidance](https://learn.chatgpt.com/guides/best-practices) and [Google's review guidance](https://google.github.io/eng-practices/review/reviewer/looking-for.html).

Avoid speculative general-purpose layers and repeated defensive coercion inside trusted domain code. Necessary authorization, cancellation, and validation at real boundaries remain essential. Tests must expose the reported failure rather than mirror private implementation details. UI checks use an actual browser with controlled providers, following [Playwright's guidance](https://playwright.dev/docs/best-practices).

The before/after comparisons in this work use identical fixtures, delayed responses, account transitions, dates, and viewport conditions. They are controlled engineering comparisons, not a randomized user A/B experiment. No claim of improved conversion, satisfaction, or empirical preference is made; a real experiment would additionally need hypotheses, guardrail metrics, randomization, reliable telemetry, and power analysis. See [Microsoft's experimentation methodology](https://www.microsoft.com/en-us/research/articles/patterns-of-trustworthy-experimentation-pre-experiment-stage/).

## Design direction

The recommended direction is a calm research workspace: make the active horizon, metric meaning, data age, and recovery state visible before adding decorative panels. [TradingView's data FAQ](https://www.tradingview.com/widget-docs/faq/data/) is useful evidence that exchange data availability and delay vary; successful retrieval is not proof of current market time. [Koyfin's saved views](https://www.koyfin.com/help/my-views/) provides a reference for task-oriented column sets. [Ghostfolio](https://github.com/ghostfolio/ghostfolio) supplies an inspectable example of a portfolio product with a mobile-first interface and simplified analytical modes. These references inform proposals rather than prove that users prefer them.

Specific next experiments:

- At 390 px, selecting symbol plus two metrics should not retain the same 1120 px minimum as a full-width table. Preserve deliberate local scrolling for dense views. W3C permits two-dimensional tables, so horizontal table scrolling alone is not a compliance defect: [Reflow guidance](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).
- Show snapshot generation date/timezone separately from quote effective time and retrieval success. Missing dates should be honestly unavailable. A weekend price is not automatically a provider failure.
- Explain rank as position in the selected ordering, rather than imply an undisclosed composite recommendation. Preserve units, benchmark/risk-free assumptions, unavailable values and the selected horizon in export context.
- Verify chart information through keyboard interaction and the equivalent data table; an aria-label alone is insufficient. Use [W3C complex-image guidance](https://www.w3.org/WAI/tutorials/images/complex/) and test the implemented interaction.
- Keep recovery close to the affected workspace. A readable session-only status and deliberate retry is more useful than silent fallback or a global error screen.

These are hypotheses with observable acceptance criteria. They are not promises of production performance or financial returns.

## Supabase evidence and deployment follow-up

Read-only inspection confirmed RLS on every listed public table. Two authenticated SECURITY DEFINER voting functions have explicit auth.uid checks, fixed search paths, atomic counters and restricted execution; advisor warnings alone do not establish an exploit. Leak-password protection was reported disabled, which requires an authorized project-setting decision rather than a code-only claim.

The live avatar bucket and three covering foreign-key indexes are absent; two profile policies retain per-row auth.uid evaluation. Existing repository migrations already describe the intended corrections. [#268](https://github.com/ParasX1/Financial-Investment-Tool/issues/268) records the deployment drift and a reviewed history/catalog reconciliation before deployment. No duplicate migration, remote reset, schema change, uploaded object, user record or credential was modified.

Grants and RLS are distinct: granting table access does not establish row ownership. Review actual deployed policies and operation requirements, then use disposable two-user tests for uploads, updates, deletion and voting. [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security) supports ownership predicates, indexed filtering and cached auth-function evaluation. Docker was unavailable here, so complete local migration replay was not claimed.

## Dependency evidence

[GHSA-p293-qw3h-jr36](https://github.com/advisories/GHSA-p293-qw3h-jr36) covers affected Pages/App Router servers on Windows filesystems; [GHSA-2xp9-vwfh-vxw4](https://github.com/advisories/GHSA-2xp9-vwfh-vxw4) describes AVIF image optimization conditions. The existing local runtime is Windows; actual production hosting/exploitability was not tested. [Next 15.5.27 release](https://github.com/vercel/next.js/releases/tag/v15.5.27) and npm peer metadata were verified before the targeted update.

Fresh lockfile comparison: production audit 6 affected packages changes from 1 critical/4 high/1 low to 0 critical/4 high/1 moderate/1 low. The separate shared installed-tree audit reported 65 propagated package findings and is not comparable to that fresh graph. Remaining sharp/PostCSS and other transitive findings require reachability/version triage. No exploitation, global force-upgrade, or assurance of complete security is implied.

Backend advisory review also identified [Flask GHSA-68rp-wp8r-4726](https://github.com/pallets/flask/security/advisories/GHSA-68rp-wp8r-4726), affecting versions before 3.1.3 under specific session/caching conditions. No Flask session usage or SECRET_KEY configuration was found in the inspected backend source, so an application-specific leak was not demonstrated. Treat upgrading the pin as maintenance follow-up, not a confirmed exploit finding.

The existing Top Picks controller intentionally forces a rebuild every 20 seconds, without a visibility gate. [#276](https://github.com/ParasX1/Financial-Investment-Tool/issues/276) records a separate workload/freshness experiment before changing that policy. It is not silently changed by the context-integrity repair.

Keep newly fixed issues open until reviewed integration; do not close them merely because a proposal exists.
